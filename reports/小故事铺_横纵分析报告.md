## 〇、先给结论

**一句话**：这不是一个「技术选型落后」的项目，而是一个**技术选型基本正确、但把风险全都堆在了"最后一公里"**的项目 —— 服务端代码干净得像样例，交付链却还停在「一个人的 shell 历史」；四天写完的 2.0 有 9,408 行 TS，而让它无法回滚、无法进 CI、无法自查版本的那几个问题，加起来不到 200 行改动。

五条具体判断：

1. **框架与数据层不用换**。Fastify 5.12.8 就是今天的稳定线（[官方基准 2026-11-01](https://fastify.dev/benchmarks/)：89,733 req/s，比 Hono 4.13.14 的 84,930 还高一档），Prisma 直读 legacy 三表是当年唯一正确的选择。**换框架、换 ORM 的收益远小于成本**，这是本次分析里我最确定的一条。
2. **真正该换的是"契约的传递方式"和"凭证的形态"**。前端 `client.ts` 里 100 行手写类型是服务端 zod schema 的第二份真相；JWT 没有 `exp`、后台 token 存 `localStorage`、全站没有速率限制 —— 这三件事和框架无关，和架构有关。
3. **交付链是最大的结构性负债**：镜像 `story-server:m4` 是可变 tag，`prod-deploy.sh` 每次重建都覆盖它，上一版退化成 `<none>`；`apps/admin/Dockerfile:54` 引用了一个**在 git 历史里从未存在过的目录**，也就是说**当前检出无法重建后台镜像**。能上线、不能回滚 —— 这是全项目最贵的一条。
4. **有两条 P0 是"能力缺口"而不是"代码 bug"**：`FIXED_SMS_CODE` 固定验证码是所有账号（含管理员）的唯一凭证；`editor` 角色可以直接把 `status` 打成 `published`，绕过审核流（`admin-routes.ts:26,142` 对 `anyRole` 开放）。它们不是写错了，是**设计上还没走到那一步**。
5. **TTS 子系统是全项目技术含量最高、也最脆的一块**。同步合成（p90 7–30 秒）挡在 HTTP 请求里、每次音频请求都写库（含 Range 请求）、缓存无淘汰 —— 而且它依赖的 msedge-tts 是**逆向 Edge 朗读接口**，微软官方对商用没有明确授权（[Microsoft Q&A，2026-09-18](https://learn.microsoft.com/en-us/answers/questions/6007729/commercial-use-of-microsoft-edge-text-to-speech-vi)）。这一块需要架构级改造，不是优化。

如果只做三件事：**① 镜像不可变化 + 修掉那个断链的 Dockerfile；② 把 136 个服务端测试搬进 CI（20 行 YAML）；③ 给 JWT 加 `exp` + 加速率限制 + 收口"谁能发布"**。做完这三件，这个项目的工程水位会从「能跑的内测」跳到「能交给别人维护」。

**五把尺子**（后面所有结论都落在这五条上）：

1. **正确性与安全** —— 会不会把不该给的内容给孩子、会不会被人登进后台、数据会不会丢。

5. **单位人力产出** —— 同样的功能，一个人（或一个 agent）要花多少小时。

第 5 把尺子对这个项目特别关键，因为它是**「文档驱动 + AI 协作」的产物**：2026-11-09 到 11-12 四天出三端，这件事本身就是它最大的技术资产，也是它最大的债主（后文 §6.3）。

### 2.3 一条主线：边界回收

把五年压成一句话：这条历史不是「技术升级」，是**边界的逐步回收**。

## 三、现状技术地图（事实层）

### 3.1 服务端：干净的分层，松散的接缝

```
index.ts ──► buildApp(app.ts) ──► 6 个 register*Routes
                                ├─ content（公开读 / home 聚合）
                                ├─ audio（TTS + Range）
                                ├─ auth（guest / phone / admin login）
                                ├─ user（me / children / settings）
                                ├─ play（progress / favorites / plays）
                                └─ admin（dashboard / stories / review / analytics / accounts / audit）
                                     │
                                     └─► services/*（业务）──► Prisma（public legacy + app 新表）
```

分层是干净的：route 不写 SQL、service 不碰 HTTP、错误统一成 `AppError` → `setErrorHandler` 映射（`app.ts:102-114`）。`contract.ts` 里 `ok()/fail()` 的封套 + `ErrorCode` 常量，前后端一致。

但接缝是松的，四处：

**① 鉴权靠"传函数"，不靠 hook。** `buildApp` 里定义 `requireAuth` / `requireRole`，然后**当作参数传给每个 register 函数**（`app.ts:91-96`）。后果：新加一个路由文件，忘记调 `requireAuth` 就没有鉴权，而且没有任何东西会提醒你。Fastify 有现成的 `app.decorate('requireAuth', fn)` + `preHandler`，甚至 `@fastify/auth`。

**② `requireRole` 每次回库查账号**（`app.ts:53-63`）。注释写得很清楚为什么（token 里的 role 不可信，停用/降级必须以库为准）—— 这个判断是对的，代价是**每个后台请求多一次 DB 往返**，且没有缓存。后台 QPS 低，现在无感；一旦接了数据大屏轮询就会显形。

**③ JWT 没有过期时间。** 三处 `app.jwt.sign({ sub, role })`（`auth-routes.ts:23,30,67`）都没传 `expiresIn`，`app.ts:36` 注册插件时也没设默认值。`@fastify/jwt` 的语义是「你不给就不加 `exp`」—— 也就是说**签发出去的 token 永不过期，且没有吊销机制**。后台唯一能做的吊销是改 `account.status`（因为 `requireRole` 回库查），App 端连这个都没有。

**④ 全站没有速率限制。** `package.json` 里没有 `@fastify/rate-limit`，`/api/auth/register-device` 每调一次就建一个游客账号，`/api/auth/send-code` 无频率控制，`/api/admin/auth/login` 无失败计数与锁定。

### 3.2 数据层：映射正确，查询有暗坑

Schema 那 261 行写得很讲究：`@@map` 对齐 snake_case、`@@schema` 区分 `public`/`app`、注释里写清 `length` 是字数不是时长、`categoryName` 是冗余列且「读取以 `category.name` 为准」。这是把「生产库真相」写进代码的范本。

暗坑在查询侧：

- **列表分页是 `count` + `findMany` 两条查询**（`content-service.ts:62-71`），无游标、无稳定排序保障（`orderBy: { id: 'asc' }` 还算稳），数据量再大就会慢。
- **搜索是 `contains` + `insensitive`**（`content-service.ts:59`）→ `ILIKE '%q%'`，任何 B-tree 索引都用不上。2,197 条无感，2 万条就会全表扫。
- **`play_event` 只有 `[at]` 一个索引**（`schema.prisma` 里 `@@index([at])`），而 Top 排行要 `GROUP BY story_id, event FILTER` 全表聚合（`admin-service.ts:127-138`），趋势要按天聚合（`:166-188`）。这张表是唯一会无限增长的表，**没有分区、没有保留策略、没有预聚合**。
- **`recordPlayEvent` 先查一次 story 存在性再插入**（`play-service.ts:82-85`），播放事件是全站最高频写，等于两倍查询。外键约束在 schema 里是有的，这次预检查是多余的。
- **全仓 0 处 `$transaction`。** 审核通过 = 改 `status` + 写 `publishedAt` + 写 `audit_log`（`admin-routes.ts:216-223`），三步不在一个事务里；正文写回 = 写 `story_content` + `story_main.length/excerpt`（`admin-service.ts:81-105`），两步不在一个事务里。中途挂掉就是「内容更新了，审计没记」。

还有一处值得单独说：`audit_log.id` 用 `audit_${Date.now()}_${Math.random().toString(36).slice(2,8)}`（9 处），这不是主键语义，是「时间戳 + 6 位随机」—— 同毫秒并发理论上可撞，而且没有任何顺序保证。Prisma 的 `cuid()` 就是为这个场景准备的。

### 3.3 音频/TTS：技术含量最高，也最脆

链路：`GET /api/stories/:id/audio` → 查正文（只允许 published）→ 缓存命中则读文件 → 未命中则**在请求里同步合成**（分块、每块限 1,500 字、块间 sleep 400ms 防限流）→ 写临时文件再 `rename` → 用 `music-metadata` 量真实时长 → 回填 `story_main.duration_sec` → 返回字节，支持 `Range` 206。

设计上有三个亮点：正文不落 Postgres（音频走磁盘，库只存索引）、先写 tmp 再 rename（并发读不到半个文件）、时长从 MP3 本身量而不是按字数估。

但有四个结构性问题：

1. **同步合成挡在 HTTP 里。** 文档自己实测：p90 内容 7–30 秒，而 App 端拉流超时 8 秒。也就是说**长故事第一次被点开时会降级**。这不是慢，是设计形态问题 —— 音频合成应该是后台任务，接口应该返回 `202 + retry-after` 或直接给占位音频。
2. **没有 single-flight。** 两个并发请求同时未命中 → 两次完整合成（`tts-service.ts:123-162` 之间没有任何锁）。一个热门故事上线首日，等于把上游按倍数暴打。
3. **每个音频请求都写库。** 命中缓存要 `update hitCount + lastHitAt`（`:129-132`），再 `backfillStory`（`:134`）；而**播放器一次播放会发多个 Range 请求**，每一个都走完整条路径 → 一个请求被放大成 N 次写。这是全仓唯一「读接口写库」的地方。
4. **缓存无淘汰。** `AUDIO_CACHE_DIR` 是命名卷（`docker-compose.prod.yml:61`），只进不出；`audioCache` 表里 `hitCount` 记了但没人读。2,197 条全量合成的量级是 GB 级。

### 3.4 后台：小而清楚，但契约靠人眼

`App.tsx` 两组路由（`/login` + 8 个受 `RequireAuth` 保护的路由），`api/client.ts` 一个 298 行的封套客户端，9 个页面全部静态导入。63 个测试、无快照、主要靠 `data-testid` + 文案 —— 密度对一个内测后台来说是够的。

三个结构性问题（`reports/team/admin-analysis.md` 有完整证据链，我抽查后认同）：

- **类型是手写镜像。** `client.ts:113-214` 100 行类型注释写「对齐 apps/server 的 admin-routes.ts」；服务端 `contract.ts` 里已经有 zod schema。`pnpm-workspace.yaml` 声明了 `packages/*`，但**仓库里不存在 `packages/` 目录** —— 「契约先行」写在架构文档第 3 行，落地时断在了这里。
- **401 只清 localStorage，不清 React 状态**（`client.ts:98-101` vs `auth.tsx:20,35`）→ 用户停在「看着像登录、每个接口都 401」的中间态。
- **前端无 RBAC 门控。** `App.tsx:45-73` 只有 `isAuthed`；editor 能看到「新增管理员」按钮（`SystemPage.tsx:271`），点了才吃 403。更严重的是服务端：`PATCH /api/admin/stories/:id` 对 `anyRole` 开放且 `status` 是可选字段（`admin-routes.ts:26,142`）→ **editor 可以把草稿直接改成 `published`，绕过 `POST .../review` 的 `adminOnly` 闸门**（`:209`）。审核流在代码层面是可以被绕开的。
- **静态层少了两道最便宜的防线。** 只给 `= /index.html` 设了 no-cache，而用户实际打开的是 `/`（`try_files` 兜底，没有 cache 指令）；全站也没有任何安全响应头（`nginx.conf:61-72` 里只有 gzip 与 cache）。后台是公网域名，这两处的修复成本都是几行配置。
- **审计留痕是断的。** 9 处 `auditLog.create`，覆盖登录、提审、审核、分类增改、推荐位增删、账号变更 —— 但**故事元数据 PATCH（标题/年龄档/分类/上下架）一个字都不记**，而前端 `SystemPage.tsx:20` 还预置了 `category.update` 标签。运营出问题时，「查是谁改的」这一步直接失败。

### 3.5 交付链：能上线，不能回滚

流程是：改代码 →（可选）`preflight.sh` → `git push`（CI 只跑类型检查 + 后台单测）→ 上 NAS 手敲 `prod-deploy.sh` 的 `backup → build → migrate → up → smoke`。

四个硬伤（每一条都有 `reports/team/infra-analysis.md` 的逐行证据）：

1. **镜像 tag 可变。** compose 写死 `story-server:m4` / `story-admin:m4`（`:31,104`），`build` 每次覆盖同一标签。上一版镜像退化成 `<none>`，**没有应用层回滚**。
2. **后台镜像当前无法从干净检出重建。** `apps/admin/Dockerfile:54` 是 `COPY apps/admin/public apps/admin/public`，而 `apps/admin/public` 在**全部 git 历史里都不存在**（`git log --all -- apps/admin/public` 为空）。200 OK 的镜像只能来自某个带未入库文件的构建现场；CI 不构建镜像，所以这个断链一直没人发现。
3. **迁移与应用不原子。** `migrate.mjs` 逐语句执行、成功后写账本，`split-sql.mjs:40` 还专门剥掉了 `BEGIN/COMMIT`；没有 `down` 迁移；执行器接受任何 `DATABASE_URL`，连生产只差一次手滑。
4. **`up` 不验健康。** `sleep 15` 后只 `grep` 容器名（`prod-deploy.sh:119-127`），容器 unhealthy 也报成功。

外加两个"门禁假象"：`preflight.sh:15` 默认 `TARGET_DB=story_m12_rehearsal`，而这个库在 11-14 已经被清掉 —— 迁移检查会静默 SKIP；`scripts/autoloop/poll-prod.sh:24` 默认 `CONTAINER=story`，1.0 退役后这个容器不存在，**版本漂移探测永远不触发**，脚本自己第 65 行还写着「2.0 容器没有 revision 标签」。

### 3.6 测试与门禁：真库是刚需，CI 是空白

`run-tests.mjs` 是这个项目里我最欣赏的一段工程代码：它用 **Postgres 会话级咨询锁**（`pg_try_advisory_lock(741852963)`，专用 `connection_limit=1` 连接）串行化所有测试进程，注释里写清了事故现场（「两条迁移同时 `REVOKE ALL ON ALL TABLES` → `tuple concurrently updated` → 大面积 500」）。文件锁只在同机有效，冲突在库上，锁就加在库上 —— 判断准确。

代价：每次测试都 `TRUNCATE` + 重跑迁移（`tests/setup-test-db.ts`），所以必须有真库、必须独占、必须串行。于是 CI 里只剩 `typecheck + admin test`，真正门禁落在 NAS 的 `story-preflight.timer`（每 6 小时，依赖 `dsh-dev` 容器和 `/workspace/story` 路径）。

**这是一个「把测试做到位、却把测试放错了地方」的典型。**

### 5.2 框架：不要换，但要把 Fastify 用对

[Fastify 官方基准（2026-11-01 更新）](https://fastify.dev/benchmarks/)：Fastify 5.12.7 单实例 89,733 req/s、延迟 10.63ms；Hono 4.13.14 是 84,930 req/s、11.28ms；Express 5.3.0 是 67,794。**Hono 的优势在边缘运行时和 JSX，不在 Node 常驻服务的吞吐**。这个项目是单台 NAS 上的 Node 常驻服务，既不需要 edge，也不需要换运行时 —— 换框架的唯一收益是「新鲜感」。

真正该做的是把 Fastify 的三个能力用起来，而这三件事现在都没用：

1. **`schema` + zod provider**：现在每个 handler 手写 `XxxSchema.parse(req.body)`。改成 `fastify-type-provider-zod`，schema 挂在路由上，校验在框架层、`request.body` 自动带类型、`@fastify/swagger` 直接把 OpenAPI 吐出来。这一步顺便解决了 §5.4 的契约问题。
2. **`decorate` + `preHandler`**：把 `requireAuth`/`requireRole` 从「传参数」改成「装饰器 + 钩子」，忘记挂鉴权从「静默放行」变成「类型不通过/启动报错」。
3. **`@fastify/rate-limit`（11.2.2）**：全局 + 按路由覆写。登录、发码、游客注册三个端点必须单独限流，这是 P0-1 的一半答案。

### 5.3 数据层：升 7，不换 Drizzle

Prisma 7 是 2026-03 的稳定线（`7.6.0` 起），最新 `7.10.1`；Prisma 8 还在 RC。它的变化对你这个项目**恰好是利好**：

- **Rust-free client 成为默认**：包体 ~90% 小、查询最多 3x 快（[官方 changelog](https://www.prisma.io/changelog/2025-11-19)）。对一个跑在 NAS 上、镜像 568MB 的服务端，这是实打实的收益。
- **必须显式传驱动适配器**（`@prisma/adapter-pg`）：连接池语义从 Prisma 自己管变成 `pg` 管 —— 对你是**改进**，因为现在 `createPrisma()` 完全没配连接池（`db.ts:8-13`），多实例下会各自开默认池。
- **代价清单要认**：强制 ESM（你本来就是 `"type": "module"`，无痛）、`generator output` 必填、`prisma-client-js` 未来移除、中间件 API 删除（你没用）、**postinstall 自动 generate 取消**（你的 `package.json` 有 `"postinstall": "prisma generate"`，升级后要显式保留或改到构建步骤）、`datasource.url` 移到 `prisma.config.ts`。

**Drizzle 不适合这个项目**：它的优势是「SQL 就是 TS」，而你恰恰需要 Prisma 的 `@@schema` + `@@map` 去映射一个**不能改的 legacy 结构**，并且已经用 Prisma 迁移文件把生产变更管住了。换 ORM 等于把 D1/D3 的所有辛苦重做一遍。

### 5.4 契约：这是「契约先行」这个概念唯一没落地的地方

架构文档第 3 行写「契约先行 —— 三端共用同一份契约」，`pnpm-workspace.yaml` 第 4 行写着 `packages/*`，然后 `packages/` 目录根本不存在，前台用 100 行手写类型对齐服务端（`client.ts:113-214`）。

三条路，按这个项目的体量排序：

| 方案 | 做法 | 适合度 |
| --- | --- | --- |
| **zod 共享包（推荐）** | `packages/contract` 导出 zod schema；服务端挂 Fastify schema；前台 `z.infer` 取类型 + 运行时 parse | ★★★★★ 一个仓库两个 app，最小改动最大收益；顺带解决 zod 版本统一 |
| OpenAPI 生成 client | `@fastify/swagger` 出 spec → `openapi-typescript`/`orval` 生成类型与 hooks | ★★★★ 如果未来有 Flutter 之外的第三方消费者，这个更标准 |
| tRPC | 端到端类型推断 | ★★ 需要把 REST 全改成 RPC；Flutter 客户端（已移出仓库但仍在用）无法享受 |

**别做 tRPC**。这个项目已经有 APK 在跑 REST，tRPC 会把「一个能对外说话的 API」变成「只有 TS 客户端能说话的 API」。

### 5.5 前端：两步走，别一次跳三个大版本

现状：React 18.3.1 / Vite 5.4.21 / antd 5.29.3 / RR 6.30.6 / vitest 2.1.9。最新：React 19.3.1 / Vite 8.3.8 / antd 6.7.0 / RR 7.18.5 / vitest 5.1.0。

antd 6 是 2026 年的稳定线（`6.7.0`，2026-11-04 发布），token 体系重构过。**注意一个测试陷阱**：现有测试里有 `'创 建'`、`'删 除'`、`'确 定'` 这种「antd 在两字中文按钮里插空格」的断言（`OtherPages.test.tsx:112,137,476`），升 antd 6 必破。先把这几处改成 `getByRole('button', { name: /创建/ })`，再升级 —— 否则你会以为是 antd 6 的锅。

Vite 8 的收益主要是构建速度，产物质量收益有限；而且 `vite 5.4.21` 目前挂着 8 条 OSV 通告（`GHSA-9jrq-w75r-8gcw` 等），**但全部是 dev server / Windows 相关，不进生产产物** —— 这是「该升，但不是安全问题」的典型。

`react-router` 7 不要再上升一档到 TanStack Router：9 条路由、无嵌套 data API 需求，ROI 为负。

### 5.6 测试：20 行 YAML 就能解，别想复杂

阻碍从来不是「GitHub 没有 Postgres」，是没人写那 20 行。`load-env.mjs:43` 保证 **env 优先于 `.env`**，所以 CI 里只要给 `TEST_DATABASE_URL`，`run-tests.mjs` 自己会拿咨询锁 + 建表。

```yaml
# .github/workflows/ci.yml 新增一个 job（与现有 check 并行）
  server-tests:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env: { POSTGRES_USER: storydev, POSTGRES_PASSWORD: storydev_local_only, POSTGRES_DB: story_test }
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U storydev -d story_test"
          --health-interval 5s --health-timeout 5s --health-retries 20
    env:
      TEST_DATABASE_URL: postgresql://storydev:storydev_local_only@127.0.0.1:5432/story_test
      DATABASE_URL: postgresql://storydev:storydev_local_only@127.0.0.1:5432/story_dev
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v4
        with: { version: 11.20.0 }   # 与 Dockerfile 对齐，别再写 10
      - uses: actions/setup-node@v4
        with: { node-version: "22", cache: pnpm }   # 与 Dockerfile 对齐，别再写 24
      - run: pnpm install --frozen-lockfile --registry https://registry.npmjs.org
      - run: pnpm --filter @story/server test
```

顺带把版本对齐（现在 CI 是 pnpm 10 + Node 24，Dockerfile 是 pnpm 11.20 + Node 22 —— 这是「CI 绿但镜像崩」的经典配方）。

**testcontainers 不需要**：service container 已经够，还省一个 docker-in-docker 依赖。

### 5.7 部署：不可变镜像在前，平台化在后

Dokploy 和 Coolify 都能给「一键回滚」，但两家文档都写清了同一句话：**镜像回滚 ≠ 数据回滚，没有任何平台能撤销一次不兼容的迁移**（[Coolify vs Dokploy 实测对比，2026-11-01](https://danubedata.ro/blog/coolify-vs-dokploy-european-vps)、[Dokploy vs Coolify 选型](https://milanjovanovic.tech/blog/dokploy-vs-coolify)）。

所以顺序必须是：

1. **先做不可变产物**：tag 带版本 + sha、打 `org.opencontainers.image.revision` label、compose 改成 `${STORY_SERVER_IMAGE}`、回滚 = 改回上一个变量值再 `up -d`。
2. 再加人工批准闸门（GitHub Environments）。
3. 最后才考虑平台化 —— 而且**别用 Watchtower**：它会在迁移没跑的情况下替换容器，这正是 1.0 时代的老毛病。

### 5.8 TTS：这是唯一一个「必须换」的技术决策

三个事实叠在一起：

- **授权不明**：微软在 2026-09-18 的官方 Q&A 里明确：Edge Read Aloud / `edge-tts` **没有公开发布商业再分发授权**，商用受支持的选择是 Azure AI Speech TTS（[来源](https://learn.microsoft.com/en-us/answers/questions/6007729/commercial-use-of-microsoft-edge-text-to-speech-vi)）。
- **价格可算**：Azure Neural TTS $15/百万字符，Free F0 每月 50 万字符（[Azure 定价](https://azure.microsoft.com/en-us/pricing/details/speech/)、[第三方核对 2026-10](https://www.cartesia.ai/learn/top-microsoft-azure-text-to-speech-alternatives)）。2,197 条故事、平均 2,000 字 ≈ 440 万字符 ≈ **一次性 66 美元**，之后增量按新增内容算。这个量级对一个家庭向产品完全可以接受。
- **自托管有解**：CosyVoice2-0.5B 是 Apache-2.0、单路实时约 4GB 显存、首包 ~1.5 秒（[2026 开源 TTS 实测对比](https://www.cnblogs.com/sensorsen/p/21367537)）；没有 GPU 时用 Piper（<50ms，音质一般）或 MeloTTS（200–400ms）做降级。

| 方案 | 音质（中文儿童向） | 成本 | 合规 | 运维复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- |
| msedge-tts（现状） | 8.5/10（云希音色确实好听） | 0 | **不明** | 低（但随时可能断） | 内测可用，商用前必须换 |
| Azure Neural TTS | 8.5/10 | $15/1M 字符 | 明确 | 低 | **首选**，改一个 adapter |
| 阿里/讯飞/腾讯云 | 8.5/10 | 同量级 | 明确（国内） | 低 | 国内上线首选 |
| CosyVoice2 自托管 | 9/10 | 一次性 GPU | Apache-2.0 | 高（要 GPU + 推理服务） | 想省钱/防断供时上 |
| Piper / MeloTTS | 6–7.5/10 | 0 | 开源 | 低 | 只做离线降级 |

**架构上更重要的一点**：换厂商只是改 `synthesize()` 一个函数，但如果不同时把「同步合成」改成「后台任务 + 状态查询」，那么换哪个厂商都救不了 8 秒超时。**这两件事要一起做。**

### 5.9 同类参照：儿童音频产品的三个通用约束

参照 Storynory、Little Fox、喜马拉雅儿童、凯叔讲故事这类产品，以及 `audiobookshelf` 这类开源自托管有声书服务，能给这个项目的只有三条，但每条都指向架构：

1. **音频必须与请求解耦**（预生成 + CDN/对象存储 + 断点续传）。所有跑量的儿童音频产品都不在请求里合成 —— 你现在正在踩这个坑。
2. **内容安全是产品功能，不是过滤器**：年龄分档必须在**查询层默认生效**（这个项目做对了：`/api/home` 的 `ageBand` 默认 `3-6`，`content-service.ts:138-144` 的兜底也绝不放宽年龄档），并且要有**人审留痕**（这个项目做错了：故事 PATCH 不写审计）。
3. **家长控制是独立的信任边界**：家长门（`parentGate`）、每日时长限制、儿童档案 —— 这些字段在 schema 里都有（`Setting`），但服务端只有 CRUD，**没有任何一处基于 `setting.dailyLimitMin` 做控制**。这是产品缺口，不是技术缺口。

## 六、横纵交汇：为什么它长成这样，天花板在哪

### 6.1 三个优势，都能追到具体的历史节点

**① 契约与错误码统一** —— 追到 `02-architecture.md` 的第一行「契约先行」。这不是洁癖，是 1.0 的教训：老站前端直接拼 pREST 的 JSON，字段名和语义散在 `js/app.js` 的 900 多行里，改一个列名要全局搜。2.0 用 `{ok, data}` 封套 + `ErrorCode` 常量把这件事一次性钉死，代价是「前端类型要手抄一份」—— 而这个代价，恰好就是 §5.4 那个没落地的 `packages/`。

**② 真库测试 + 时区正确** —— 追到 `03-decisions.md` §9：睡前时段按 UTC 归桶得 6.2%、按 `Asia/Shanghai` 得 66.1%。这个 bug 用 mock 永远抓不到。于是「测试必须真 Postgres」成了硬约束，`run-tests.mjs` 的咨询锁、`getAnalyticsTrend` 里那句「不能用 `CURRENT_DATE`」的注释（`admin-service.ts:159-163`），都是这条约束长出来的。**这是这个项目最值钱的工程资产**，任何时候都不要为了「让 CI 跑起来」把它降级成 mock。

**③ 内容安全的默认值设计** —— 追到 `00-research` P1（恐怖/怪谈/推理不进儿童端）。落地方式很讲究：`/api/home` 的 `ageBand` **默认 3-6 而不是"不过滤"**，兜底逻辑「可以放宽 category/featured，绝不放宽 ageBand」（`content-service.ts:128-144`），音频接口对草稿返回和不存在一样的 404（`audio-routes.ts:63-66`）。这是「安全路径就是默认路径」的正确写法，比任何 WAF 都可靠。

### 6.2 三个天花板，也都能追到具体的历史节点

**① 不可变产物缺席 → 天花板是「不敢改」**。因为镜像 tag 可变、没有 registry、没有 revision label，所以「回滚」这件事在 2.0 里是不存在的。一个不敢回滚的系统，最终会演变成「不敢动生产」—— 于是所有改动都堆到下一次大版本，于是大版本风险更高。这条的根在 D7 之后那套「生产只读 + 手工部署」的纪律：纪律本身是对的，但它替代了「自动化」，而不是被「自动化」替代。

**② 单机单实例 → 天花板是「不能长」**。`story-dev-postgres`、`dsh-dev` 容器、NAS 上的 timer、`/workspace/story` 路径、宿主机上的 `.env.prod` —— 门禁、测试、部署、备份全部绑在一台机器上。这不是技术选择，是资源现实（一台 NAS + 一台桌面机）。它的代价不是性能，是**「关机即失守」**：NAS 停一天，门禁停一天，而且没人会知道。

**③ legacy schema 直读 → 天花板是「不能改语义」**。`length` 是字数不是时长、`category_name` 是冗余列、`category_id` 可空、`story_content.storyId` 可空且 unique —— 每一个都在代码里留了一条注释和一段兜底逻辑。这是 D1 的正确代价，但它意味着**任何数据模型层面的产品创新都要先绕开这层**。举例：想做「系列/合集」，就得新开表 + 新开接口，而不是给 `Story` 加一个 `seriesId` 就完事。

### 6.3 「四天写完」这件事的真实含义

这一节是我最想说的，因为它决定了「该不该继续用这套方式做下一个版本」。

四天出三端（服务端 136 测试 / 后台 63 测试 / App 58 测试 / 端到端 16 步）是真的。但要看清楚这个速度的**构成**：

- **可复用的部分**：文档先行（M0 三份文档把不确定性提前消化）、契约先行（前后端不必互相等）、真库测试（错误在写的时候就暴露）、以及「一个 agent 能在同一台机器上同时改三端」。
- **被推迟的部分**：CI 接入、镜像不可变化、鉴权形态、审计完整性、TTS 异步化 —— 也就是本文档 §4 里的 P0/P1。**它们不是被漏掉了，是被排到了「上线之后」**，而上线之后就没有之后了（这是所有「先上线再补」项目的共同命运）。

所以结论不是「这套方式不好」，而是：**这套方式擅长把「功能」推到生产，不擅长把「运维契约」推到生产**。补的方法不是放慢速度，是给流程加一条硬规则：**每个里程碑必须同时交付它的「不可逆性清单」**（回滚怎么做、漂移怎么发现、审计记在哪、谁有权发布）。这次上线缺的就是这张清单。

### 6.4 三个剧本

**最可能（60%）：内测状态长期维持，债按需偿还。** 用户是家庭/小范围，QPS 低，固定验证码靠「手机号不外泄 + 8 位随机码」撑着，TTS 用 Edge 接口撑着，回滚靠 `pg_dump` 撑着。半年内不会出事，但一旦要接真实短信、要上应用商店、要第二个运营人员，就会在同一个季度里同时撞上 P0-1（凭证）、P1-4（不能回滚）、P2-18（TTS 授权）三堵墙。

**最危险（25%）：`play_event` 与音频缓存把 NAS 撑爆，或在一次迁移里半死。** 触发路径很具体：某条故事被反复分享 → 音频合成并发打满上游 → 进程内存与 CPU 争抢 → 容器被 OOM kill → `restart: unless-stopped` 拉起 → 又打满。或者更简单：一次 `prisma migrate` 中途失败（无事务），账本没记，重跑时迁移文件不幂等 → 手工救库。

**最乐观（15%）：按 §7 的路线做完，它变成一个「可以交给别人」的项目。** 判据不是功能变多，而是：新人 clone 下来能一条命令跑全测试、能一条命令回滚上一版、能一眼看到生产跑的是哪个 sha、能在审计里查到「谁把这条 9+ 内容放进了 3-6 首页」。做到这四条，这个项目就从「一个人的作品」变成「一份资产」。

## 七、改造方案：按投入产出排序

### 7.1 本周（P0，约 1.5 人日，全部可逆）

**① 给 JWT 加过期 + 加速率限制 + 收口发布权**

```ts
// apps/server/src/app.ts
await app.register(jwt, {
  secret: opts.jwtSecret,
  sign: { expiresIn: '2h' },          // 后台 2h，App 端可另签 30d
});
await app.register(rateLimit, { global: false, max: 100, timeWindow: '1 minute' });

// 登录/发码/游客注册三处单独收紧
app.post('/api/admin/auth/login', { config: { rateLimit: { max: 5, timeWindow: '5 minutes' } } }, handler);
app.post('/api/auth/send-code',   { config: { rateLimit: { max: 3, timeWindow: '10 minutes' } } }, handler);
app.post('/api/auth/register-device', { config: { rateLimit: { max: 10, timeWindow: '1 hour' } } }, handler);
```

**② 把 `status → published` 收成 admin-only**

```ts
// admin-routes.ts：PATCH 里把 status 从 StoryPatch 拆出来
const StoryMetaPatch = StoryPatch.omit({ status: true });
// 命中 status 时单独校验角色
if (body.status === 'published') await requireRole(req, adminOnly);
```

**③ 修 `apps/admin/Dockerfile:54` 的断链** —— 删掉那行 `COPY apps/admin/public ...`（该目录在全部 git 历史里都不存在），并在 CI 加一步 `pnpm --filter @story/admin build`，让这类断链在 PR 阶段就红。

**④ 给 `preflight.sh` 与 `poll-prod.sh` 改默认值** —— `TARGET_DB` 默认改 `story_dev`，`CONTAINER` 改 `story-server-prod`。两个字符的改动，把两个「永远绿的假门禁」变成真门禁。

**⑤ 加事务与审计**：审核通过、正文写回用 `db.$transaction([...])`；`PATCH /api/admin/stories/:id` 补一条 `audit_log`（带 before/after 的 diff）。

### 7.2 本月（结构，约 5 人日）

**⑥ 136 个测试进 CI**（§5.6 的 YAML）+ 对齐 Node/pnpm 版本。
**⑦ 不可变镜像**：tag = `v0.1.3-<sha>`，打 `revision` label，compose 用 `${STORY_SERVER_IMAGE}`，跑一次「上 v0.1.3 → 回 v0.1.2」的真回滚演练。
**⑧ `packages/contract` 落地**：先生成 `packages/contract/src/{story,user,admin}.ts`，服务端改为从这里 import schema，前台 `z.infer` 取类型 + `client.ts:93` 处 `schema.parse`。这一步同时把 zod 升到 4.6.7（顺手消掉 `GHSA-mrhx-c7xc-m3w5`）。

```ts
// packages/contract/src/story.ts
export const StoryListItem = z.object({
  id: z.number(),
  title: z.string(),
  excerpt: z.string().nullable(),
  ageBand: AgeBand,
  tags: z.array(z.string()),
  status: StoryStatus,
  // ...
});
export type StoryListItem = z.infer<typeof StoryListItem>;
```

**⑨ 迁移执行器加护栏**：`migrate.mjs` 启动时校验 `DATABASE_URL` 的库名白名单（`story` 需 `--i-know-what-i-am-doing` 标志）；每个迁移文件包在一个事务里执行（把 `split-sql.mjs` 剥掉的 `BEGIN/COMMIT` 还回来，只在确实需要 `CREATE INDEX CONCURRENTLY` 的文件上保留例外）。

**⑩ 音频接口去写放大**：命中缓存不再 `update hitCount`（改成异步/抽样），`backfillStory` 只在首次合成后调；Range 请求只 stat + 读文件，不走合成路径。

**⑪ TTS 异步化**：`GET /api/stories/:id/audio` 未命中时返回 `202 + Location`，由后台 worker 合成（Prisma `audioCache.status = pending|ready|failed`），App 端轮询或用 `Range: bytes=0-` 重试。这一步同时接上 Azure/阿里云的 adapter。

### 7.3 本季度（架构，需预算）

**⑫ Prisma 7 + 驱动适配器**（按 §5.3 清单逐项，预计 1 人日，风险集中在 `postinstall` 与 `output` 路径）。
**⑬ 后台迁 TanStack Query + 401 联动 + ErrorBoundary + 路由级懒加载**（一并解决 `AppLayout` 每次导航重复拉 dashboard 的问题）。
**⑭ `play_event` 分区 + 日聚合表**：按月分区（`PARTITION BY RANGE (at)`）+ 一张 `app.daily_metrics`，看板读聚合表，保留策略 12 个月。
**⑮ 可观测性最小闭环**：`/api/ready`（写路径探针）、`/api/health` 返回 `{sha, buildTime}`、compose 加 `logging.max-size`、告警第二出口 + dead-man switch。
**⑯ antd 6 → Vite 8 分两步**（先改测试里的中文按钮断言，再升 antd）。

### 7.4 明确不要动

| 不要动 | 理由 |
| --- | --- |
| HTTP 框架换成 Hono/Nest | 基准上无收益，改造面 100%，生态插件（cors/jwt/rate-limit）已经够用 |
| Prisma 换 Drizzle/Kysely | 你最大的约束是「映射不可改的 legacy 表」，这正是 Prisma 的强项；换 ORM 等于重做 D1/D3 |
| 引入 Turborepo/Nx | 2 个 app、9,408 行，构建缓存收益小于配置成本 |
| 真库测试降级成 mock | 时区、迁移、并发这三类 bug 只有真库能抓，这是全项目最值钱的资产 |
| 上 Watchtower/自动重启式部署 | 会在迁移未跑时替换容器，1.0 时代已经吃过这个亏 |
| 上 tRPC | 已有 APK 在跑 REST，会把 API 私有化成只有 TS 客户端能用 |

### 7.5 验收口径（怎么证明改完了）

不是「测试通过」，是这五条：

1. 干净 clone → `pnpm install && pnpm -r test` 全绿，**不需要**连任何一台已有机器。
2. 干净 clone → 两个镜像 `--no-cache` 都能构建成功。
3. 生产回滚演练：`v0.1.3 → v0.1.2` 用时 < 2 分钟，且期间 `api-story` 无 5xx。
4. `/api/health` 返回的 sha 与 `git rev-parse HEAD` 一致。
5. 审计表里能查到「某条故事的 `age_band` 从 `3-6` 改成 `9+`，谁改的，什么时候」。
