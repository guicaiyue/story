## 0. 先校正一条时间观

**git 史 ≠ 工作史。** 153 个提交里，2025-04 → 2025-11 是零散的「update / 添加和优化功能」，2026-08 → 2026-09 才有语义前缀，而 2.0 的全部重写（M0 文档 → M1 → M2 → M3 → M4 → 上线验证）发生在 **2026-11-09 至 11-12 四天内**，却只在 **11-13 一天**落成 5 个提交（218 文件、约 4.5 万行）。这条不同步本身就是史料：它证明「代码先进工作树、后进 git」是四年一贯的工作方式，也直接造成了 0.1.1 源码永久缺失这类不可逆损失。

## 1. 阶段划分（5 段）

### 1.0 静态站期（2025-04-25 – 2025-11-26）

- **核心特征**：一个人的个人站。第一版（`9847ee5`/`12cf1da`）拉的是公开第三方故事 API（mxnzp.com），README 自称「故事收集平台」；5 月中下旬接入 supabase-js 并目录化（`1295805`）；此后陆续加访问量统计、Live2D 看板娘、页面级 Edge-TTS 朗读（`32eb331`）、`add.html`/`app.html` 两个**写入页**（`6e1aa2c`）。提交信息是「update」「优化！！！」「测试提交」。
- **核心矛盾**：内容与体验持续变好，但产品模型停在「内容展示」——没有账号、没有进度、没有后台（00-research §2 的判断：「是一个内容展示站，不是一个产品」）；同时**没有任何工程约束**：无测试、无环境区分、无发布流程。

### 1.0 工程化期（2026-08-09 – 2026-09-07）

- **核心特征**：给个人站补管道。一次 `dockerize + CI 推 Docker Hub`（`d4629d2`）、SPA 路由与 nginx fallback（`7cc76cb`/`561ea74`）、Edge-TTS 改为前端直连（`b2b350b`）、纯 Traefik 部署解决端口冲突（`a1e75aa`）；随后接入 PageSpy 远程调试（`5ebced0`，产品化为「站长支援」）、自建 Umami 埋点（`f0fdf92`）、环境分离 + n8n Watchtower 部署（`9b571bc`/`1880098`）、配色柔化（`b341a02`，走 `release/story-calm-20260907` 分支）。
- **核心矛盾**：管道被加固了，**被加固的却是一个错误的数据面**——`eaa97e2`（09-03）把数据层从 supabase 换成 pREST，同时**删掉全部写入路径**（`add.html`/`app.html`/`js/add.js`，-737 行）：写入能力被砍，运营仍要改数据库；而 pREST 的配置（不鉴权、不限制表、超级用户连库）两个月后被实测为「公网可写、只靠可伪造的 UA 拦」（03 §7）。工程化没有降低风险，反而把风险搬到了公网。

### 2.0 重建期（2026-11-09 – 2026-11-12）

## 3. 六个「为什么」的因果还原

**① 为什么从 pREST + 静态站转向自建 Fastify？**
不是因为它慢，而是它**承担不了「人—内容—时间」的关系**。00-research §2 把 1.0 判为「内容展示站」，痛点 P2/P3/P5/P6 全在 pREST 能力之外：无账号、无进度/收藏、无后台、无数据闭环。更关键是通道本身**成了风险源**：03 §7 实测公网可达（`8.137.162.154`）、WAF 只按 User-Agent 拦、写方法能穿透到 Postgres 并以超级用户执行——2197 条内容「处于可被公网改写/删除的能力之下，唯一拦阻是一层可被任意伪造的 UA 检查」。故 D2「保留 pREST 只读」从一开始就是过渡态，最终由 D9 推翻。

**② 为什么 Prisma 直接映射 legacy 表、不做数据迁移？**
因为**数据已经在目标库里**。08 §2.1 逐条验证老站与生产库读同一份数据（`story_main=2197`、标题逐条一致），迁移只会把 2197 行从同一个库搬到同一个库，还会立刻打断仍在服务的老站。故 D1 定「不做迁移、不做 legacyId」，D3 定「新列 `ALTER TABLE` 追加，不建伴随表」——**改的是结构，不是数据**。代价写进同一批决策：D7 生产只读、只产出迁移文件，以及 03 §1 记下的全部不匹配（无 `content`、无 `slug/tags/status`、`length` 是字数、`category_id` 可空、`category_name` 冗余）。

**③ 为什么 1.0 被彻底删除（D9）？**
三个理由叠加：**(a) 语义上已被替代**——D9 原文「推翻 D2」，1.0 的前提（唯一数据通道）在 2.0 上线后消失；**(b) 安全上不能留**——03 §7 的 pREST 敞口是老站专属路径，下线即消险，比继续打补丁（`04-prest-hardening-plan.md` 四处改动）更彻底；**(c) 双栈太贵**——`43eaa3c`「根 `.dockerignore` 改白名单，避免 2.0 源码进静态站镜像」是最直接的证据：一个仓库两套构建上下文，任何仓库级文件都要同时伺候两边。删除**可逆**（NAS `retire-1.0-20261114-000508/` 归档 2.8 MB/57 条目 + git 父提交 `499f138`），「彻底」指工作树，不指档案。

**④ 为什么测试必须真 Postgres？**
要验的东西**只存在于 Postgres 的语义里**：① 统计口径——睡前时段按 UTC 归桶得 6.2%、按 `AT TIME ZONE 'Asia/Shanghai'` 得 66.1%（03 §9），mock 会把这条 bug 稳稳藏住；② 迁移语义——非空老库上 `prisma migrate deploy` 必报 P3005，才有自维护账本的 `migrate.mjs`（07 §4.1）；③ 迁移发现——测试库曾写死只应用 `init`，新迁移「静默不生效」，测试对着过期 schema 也全绿（03 §11.4-5）；④ 并发——两条测试流同时建表删表会互相破坏，故 11-13/14 加咨询锁并串行化 `test:setup`（`d1d407a`/`bc3603e`/`3db06a4`）。推论是硬约束：CI 无库 → 真门禁是 NAS 上每 6 小时的 `story-preflight.timer`。

**⑤ 为什么推 `main` 不发布？**
因为 1.0 那套链条里推 `main` 就是发布（1.0 README：「唯一发布入口是推送到 `main`」，CI 跑四个契约测试 → 推 Docker Hub → Watchtower 拉镜像）。2.0 把这条链**主动切断**：服务端 136 个测试要 Postgres，GitHub Runner 上没有；生产镜像是本地构建（568 MB / 64 MB，全层 CACHED）；上线是 11 个带断言的写操作，必须人批。于是 `db0c05c` 后的 `ci.yml` 只做「类型检查 + 后台单测」并把理由写进注释，`AGENTS.md` 第 5 条升格为硬约束。代价是**发布通道从自动变手动**，收益是发布不会被一次 `git push` 意外触发。

**⑥ 为什么只有 0.1.2 一个版本？**
三次版本事故的合并结果：0.1.0 的包**根本不能用**（基址被 `String.fromEnvironment` 的 `defaultValue` 编成 `http://127.0.0.1:3000`，release 清单还缺 `INTERNET` 权限，`aapt2` 实测只有 `ACCESS_NETWORK_STATE`）；`v0.1.1` 指向的提交里**没有任何 App 源码**（只有 1.0 静态站），发 release 会「有 tag 无内容」；`0.1.1+2` 的 pubspec 改动**从未进过 git**（`git log --all -S` 只命中文档，核实后判定「不要再找」）。既然前两个版本语义上都无法交付，处置就从「保留历史」改成「清理到只剩可信版本」：删 tag、删 Release、删 0.1.1 的两份文档与 sha256（`2870cb8`，-339 行）。0.1.2 恰是第一个「正确基址 + 正式签名 + versionCode 3」的包。

## 5. 决策台账 D1–D9 要点

- **D1 数据库**：M1 不做数据迁移、不设 legacyId，Prisma 直读既有三表；迁移文件是唯一交付物。
- **D2 pREST**：M1 保留 pREST 只读通道作为老站入口，不改动、不设弃用时点。**（已由 D9 推翻）**
- **D3 老表扩列**：新字段直接 `ALTER TABLE` 追加在 `story_main`，不建伴随表；只在 dev 执行，生产仅产出 migration。
- **D4 鉴权**：手机号 + 固定验证码走通 JWT 全链路，不接真实短信，仅预留 adapter；M3 前替换。
- **D5 文档**：授权在 `docs/product/` 追加决策记录，00/01/02 保持只读。
- **D6 游客升级**：游客账号升级规则 M1 不定稿，`Account.phone` 必须可空且唯一；「可升级」不作 M1 验收项。
- **D7 生产库只读**：禁止对生产 `story` 库任何写操作，开发一律用独立 dev 库，生产只产出 migration 文件；收权脚本待批准。
- **D8 新表 schema**：用户/儿童/播放/运营新表全建在独立 schema `app`，不向 pREST 角色授权；共库 ≠ 共 schema。
- **D9 1.0 彻底删除**：2026-11-14 两步——先下线（容器/镜像/部署目录/两条 Traefik 路由），再删源码与它专属的构建、开发、测试三件套，CI 从「四个契约测试」换成「2.0 类型检查 + 后台单测」；归档在 NAS 与 git 历史。

## 6. 开发方式的演变：从手写 HTML 到 autoloop 中台

**四个世代**：① 2025 年，一个人对着 `index.html` 直接改，提交信息就是「update」；② 2026-08–09 有 CI、镜像、release 分支，仍是单人直线操作；③ 2026-11-09 起**文档驱动 + 任务卡闭环**——产品负责人只做调研/拍板/验收，开发 agent 读文档写代码，观察者回合末建卡、决策秘书出票拟、面板批准后派发回原会话（`06-working-baseline.md`）；④ 2026-11-13 起**autoloop 中台**——人写 issue、agent 自己接活跑验收开 `feature/*` 回执，生产漂移/宕机/预检失败由探针发事件，只读的活派 NAS 侧、改代码的活派本机（`scripts/autoloop/README.md`）。

**收益（有数字）**：决策成本从「手写 4 条 200–400 字指令」降到「3 条消息 + 3 次点击」（05 §3）；决策留档可审计（卡片账本 + `/stats`）；危险动作有了前置闸门（`rm -rf /tmp` 实测被拦并建卡）；上线当天「一句话进、11 个带断言的动作出」。最有说服力的是 `noise.asks.autoRate = 1.0`：闸门六次判断「要不要问人」，人一次没答——这条数据直接推翻了「工具调用时问人」，把提问时机挪到回合末。

**开销（同样有数字）**：① 状态机不闭环——批准后卡停在 `unknown`、仍在「要我决策」，导致重复批准与重复派发（05 §2A/§2B）；② 闸门误判——文档里写 `DROP`、`rm -rf` 字样也判 destructive（04 §28.4/§29.3），dev 库的 DROP 还被标成 `prod-db:conn:prod`（11 §6）；③ 观察者时机脆弱——70 分钟长回合不触发观察者（05 §7）；④ 度量自身被污染——跑测试会把计数写进真实账本，后才隔离（22 §⑦-6）；⑤ 承诺与事实有落差——22 自己承认第 ⑤ 条只是**部分达成**：本轮实现是宿主侧直接改代码，插件执行层只能把答复投回原会话，没有「从卡片派生新会话」。

一句话评价：**它把「人的介入」从写指令变成点批准，却没把「批准之后是否真的完成」变成机器可判的事实**——这正是收尾要靠 `23-final-verification.md` 那种「当场跑一遍、贴原始输出」来兜底的原因。
