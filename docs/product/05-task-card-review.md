# 任务卡系统 · 真实开发场景复盘与优化

> 场景：用 dsh-dev 的开发会话把「小故事铺」从静态站升级为平台（服务端 + Web 后台 + 安卓 App），产品负责人只做调研、拍板与验收。
> 目的：用真实使用暴露问题，而不是用测试用例证明它能跑。

## 1. 这一轮真实发生了什么

| 环节 | 结果 | 证据 |
| --- | --- | --- |
| 观察者从开发会话提炼卡片 | 成功 3 次 | `records.json`：回合 2 → 3 张、回合 6 → 1 张、后续回合持续 |
| 决策秘书出票拟 | 成功 3 次（1 次 60s 超时后重试） | `records.json` decision 记录，各 3 个方案 + 推荐 |
| 面板批准 → 入队 → 派发回会话 | 成功 4 次 | journal：`case:waiting → leased → dispatched → executed` |
| 开发 agent 收到派发后继续干活 | 成功 | 会话里出现「任务卡答复 c-xxx」的 user 消息与后续动作 |
| 验收 | **失败：全部落到 unknown** | journal `verifying → unknown`，原因「没有清单也没有证据」 |
| 卡闭环 | **失败：批准后仍在「要我决策」** | 3 张卡 `status=open, deliveryState=unknown` |
| 多问题提问 | **部分失败：3 个问题被拍平成 7 个选项** | 卡片 detail + `question.items` |
| 重复拦截 | **失败：同一条答复被派发两次** | 会话里两条相同的「任务卡答复 c-mw958ol4」 |

## 2. 根因分类

### A. 验收口径错配（最严重）
决策卡执行的动作是「把一句话投回会话」，没有 todo、没有证据，但验收器按「任务型卡」的规则要求清单/证据，于是判 `unknown`。
`unknown` 不是终结态，卡不会进「已结束」，`status` 仍是 `open`，面板继续显示「要我决策」+「批准」按钮。

**修复（已落地）**：`verifyCard` 对 `kind === 'decision'` 且无清单无证据的卡直接判 `confirmed`，理由「决策已回投原会话，没有需要验收的产物」。

### B. 批准不幂等
面板保留「批准」按钮 + 状态未变 → 用户（我）点了两次 → 同一句答复投递两次。

**修复（已落地）**：
- 宿主：`approveCard` 前加 `assertApprovable`，`waiting/leased/dispatched/executed/verifying/confirmed` 一律返回 `ALREADY_APPROVED`；
- 面板：`deliveryState` 非 `idle/invalidated` 时不再渲染「批准」，改为「已批准，执行中」chip。

### C. 多问题提问被拍平
`ask_user_question` 支持一次问多题；插件把它们合成一张卡，`QuestionOptions` 把各题选项铺成一个列表，点任一选项会被当成**所有题**的答案。我这次只能绕过面板、用 API 发一段合并文字。

**未修复（下一步）**：按 item 分组渲染 + 逐题选择 + `answers: [{id, selected}]` 提交；单题卡保持现在的一键作答。

### D. 同一条待决有两个入口
原生提问组件（聊天里）和任务卡同时存在，用户不知道答哪个；我这次两边都用了。

**未修复**：提问建卡时，卡片上标注「同源：聊天里也能答」，或把原生组件折叠到卡里。

### E. 第二次提问没有建卡
只有第一次 `ask_user_question` 留下「问题卡：…」日志；第二次（schema/文档授权/pREST 权限）只有原生组件。

**未修复**：需查 `question/hook` 的 ask/askTimed 分支与 `recordQuestionCard` 的失败路径（当前异常被吞），加日志与按 callId 幂等。

### F. 回合内的不可逆动作没有闸门
开发 agent 在回合内准备「直接对生产库 ALTER TABLE」，观察者是**回合结束**才跑，拦不住。这次是我人工叫停。

**未修复（设计层）**：对 `write-code/destructive` 类工具调用加前置 guard（horon-circuit 或宿主 approval），而不是靠回合后复盘。

### G. 决策秘书 60s 超时
日志「第 1 次失败：观察者会话超时未完成」，重试成功。flash 模型 + 长上下文时 60s 不够。

**未修复**：默认超时按模型调整（建议 120s），或超时后降级为「只给推荐方案」。

## 3. 介入次数（真实数据）

| 类型 | 次数 | 说明 |
| --- | --- | --- |
| 人工消息 | 3 条（+1 条排队） | 全是方向/交付口径，没有返工指令 |
| 面板批准 | 3 次 | 0 输入，文案来自票拟 |
| 卡片作答 | 1 次 | 多问题卡被迫合并 |
| 原生组件作答 | 2 次 | 与卡片重复的入口 |
| 自动派发 | 4 条 | 我不用手写决定 |
| 人工纠偏 | 1 次 | 生产库风险，系统未拦 |

**对比基线**：如果不用任务卡，这 4 个决定需要我手写 4 条完整指令（约 200–400 字），并且要自己盯会话。
现在我的输入量约 3 条消息 + 3 次点击；**决策采集与回投已经由系统承担**，但「批准后是否完成」的确认成本被 unknown 状态浪费掉了。

## 5. 下一步优化（按价值排序）

1. 多问题卡逐题作答（C）——直接决定「决策采集」是否可信。
2. 提问建卡幂等 + 失败可见（E）——漏卡比错卡更危险。
3. 回合内危险动作前置闸门（F）——这是「不可逆」场景的唯一有效时机。
4. 原生提问与卡二选一（D）——减少认知负担。
5. ~~决策秘书超时与降级（G）~~ → 已把默认超时提到 90s。

## 6. 追加发现（第 5 轮）：记录持久化回退

**现象**：观察者/决策在 20:10、21:00 都跑过并建了卡，但 `records.json` 最新一条停在 19:46；面板「记录」页因此看不到这两轮。

**定位**：`RecordStore.add()` 用内存缓存整份覆盖文件。插件热重载会同时存在旧/新两个实例，各有一份懒加载缓存；旧实例的追加会把新实例刚写进去的条目整份覆盖掉（文件 mtime 更新、内容反而变旧）。

**修复**：`JsonDoc.readFresh()`（丢缓存重读）+ `RecordStore.add` 追加前重读；加回归用例（另一实例写入的条目不会被覆盖）。`pnpm verify` 全绿；修复后新记录立即落盘（22:10 起恢复）。

**教训**：追加型数据（记录、判例）的写入必须「先读后写」，不能依赖长生命周期实例的缓存——热重载是这个插件的一等场景。

## 7. 追加发现：长回合会吞掉观察者

- 回合 15（TTS 实现，约 70 分钟）结束后没有观察者记录（日志里没有「回合 15 → ...」），紧接着 turn 16/17/18 由排队消息快速启动；
- 回合 18 正常触发（empty 0 张卡）。
- 推测：回合结束与新回合开始挨得太近时，观察者触发被「已有新回合」跳过。**真实影响**：一次 70 分钟的工作可能不产生任何卡片，人无法介入。
- 待办：触发端对「同一会话连续回合」做排队而不是丢弃；或对长回合加中途检查点（每 N 分钟允许一次观察）。

## 8. 追加发现：失败卡不会自动对账

- 回合 20 模型工具调用格式损坏（输出裸 `<parameter name="edit">` 标记），回合提前结束；
- 观察者据此建卡「记录 settings 持久化重试再次失败」；
- 但紧接着回合 21 重发短指令后**工作已经落地**（`RemoteSettings`/`getSettings`/`loadSettings` 都在，`flutter test` 75 passed）；
- 卡上的结论已过期，面板仍显示为待处理。

**问题**：观察者只看「那一回合的回复」，不看之后的状态；失败类卡没有对账机制。

**建议**：
1. `info`/失败类卡在 `reconcile` 时按「目标产物是否已存在」自动失效（插件已有 `reconcile` 与 `invalidatedReason`，只是没覆盖这类）；
2. 观察者提示词加一条：**不要根据模型自述失败就建卡**，要给出可核验的产物路径（文件/接口/命令），否则降为 info。

## 9. 追加发现：长回合 + 坏回合都会让观察者失效

| 情形 | 现象 | 影响 |
| --- | --- | --- |
| 长回合（70 分钟） | 回合 15 结束未触发观察者 | 一次大工作不产生任何卡，人无法介入 |
| 坏回合（工具调用格式损坏） | 回合提前结束、只做了一半 | 观察者建「失败」卡，但后续重试已成功，卡过期 |
| 连续排队回合 | turn 16/17 间隔极短 | 观察者被跳过（推测同一会话新回合开始导致丢弃） |

共同点：**观察者的触发时机绑在「回合结束」这一个事件上**，而长回合/坏回合/连发回合都会让这个时机失真。需要的是「状态变化即观察」或「定时兜底观察」，而不是只靠回合结束。
