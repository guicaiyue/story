## 2. 角色

| 角色 | 谁 | 职责 | 不该做的事 |
| --- | --- | --- | --- |
| 产品负责人 | 人（我） | 调研、写产品文档、拍板、验收、统计介入 | 不直接写业务代码 |
| 开发团队 | dsh-dev 里 `story` 工作区的 agent 会话 | 读文档、写代码、跑测试、按卡执行 | 不碰生产库、不发版、不改产品方向 |

| 调度者 | 任务卡 kernel（确定性系统） | 批准 → 入队 → 派发 → 验收 | 不做内容判断 |

## 3. 一轮开发的固定动作

```
① 产品负责人给目标（带验收口径）
      ↓
② 开发会话读文档、拆任务、执行、汇报
      ↓
③ 回合结束 → 观察者建卡 → 决策秘书出票拟
      ↓
④ 产品负责人在面板上批准 / 作答（尽量只点不写）
      ↓
⑤ 调度者把批准的话派发回原会话（WIP=1）
      ↓
⑥ 开发会话继续执行 → 回合结束 → 回到 ③
      ↓
⑦ 产品负责人按里程碑验收（跑测试 / 开页面 / 看数据）
```

**每次给目标必须写清四件事**：范围、验收口径、红线、完成后怎么汇报。
**每次验收必须自己跑一遍**，不能只看 agent 说「已完成」。

## 4. 验收口径（按端）

| 端 | 验收动作 | 通过标准 |
| --- | --- | --- |

## 5. 介入指标（任务卡系统的价值度量）

**介入 = 人为了让开发继续而做的动作**。分四类，每次都记：

| 类型 | 例子 | 记法 |
| --- | --- | --- |
| 人工消息 | 给目标、纠偏、补上下文 | 会话事件 `source.kind=user` 计数 |
| 面板批准 | 点「批准」 | 卡片 journal `actor=scheduler, authority=user` |
| 卡片作答 | 答问题卡/澄清卡 | 卡片事件 `answered` |
| 返工纠偏 | 指出 agent 做错、要求重做 | 人工消息里带「不对/重做/漏了」的条数 |

**期望形态**：人工消息以「目标」为主，返工纠偏趋近 0；决策大部分由「批准」完成。
**当前基线（2026-11-09 首日）**：人工消息 4、批准 5、作答 3、返工 1（生产库风险）。

统计方式（2026-11-13 起）：`scripts/dev-metrics.mjs` 已随仓库收敛删除；需要时看任务卡插件的度量产物。
当前实测（2026-11-09 22:50，两个会话）：turns 21、human 9、cardAnswer 13；卡片 21 张、approved 7、answered 5、confirmed 9、autoApplied 1。

## 6. 红线

1. **生产库只读**：任何写操作先写脚本、等批准；开发一律 dev 库。
2. **不发版**：不 push `main`、不触发 CI、不动生产容器；上线由人单独决定。
3. **老站仍在线上**：`index.html`/`js/`/`css/` 原地保留并由 `story.xirizhi.cn` 提供服务；`legacy/` 迁移未做，也不着急做。
4. **儿童内容安全**：恐怖/怪谈默认不进儿童端；年龄分级需人工复核，不能只靠启发式。
5. **付费透明**：价格、周期、取消入口同屏；儿童端不接第三方广告。
6. **插件改动**：先改 `src/shared` 契约，再 `pnpm verify`，不调阈值。

## 10. 交接与开局的教训（2026-11-09 实测）

**跨会话交接可行**：新会话只读 `docs/product/*` + 仓库就能接班，不需要旧会话上下文。
但**开局必须限时**，否则新会话会把「核实现状」做成一场长审计：

- 第二个会话（M4）第一条消息要求「先核实再动手」，结果 turn 1 跑了 35+ 分钟、50+ 步还在探测基础镜像/缓存/dockerignore，五个交付文件一个没落盘；
- 插话「环境已确认，直接落盘五个文件，落盘后统一验证」后才回到正轨。

**写成规矩**：
1. 开局消息里给「核实预算」：最多 N 个工具调用 / N 分钟，超了就按已有信息开工；
2. 交付物清单要点名到文件路径，并要求「先落盘再验证」，避免边探边写；
3. 会话第一轮结束前必须有产物（哪怕是最小骨架），否则观察者拿不到可对账的东西。
